# Module imports and exports

<!-- Sources: guidelines/dxp/bundler_imports.md, guidelines/dxp/exporting.md, guidelines/general/imports.md -->

**Applies when the PR touches:** any `node-scripts.config.js` (keys `main`, `submodules`, `exports`, `symbols`, `typescript`, `alias`, `customBuild`); the generated `modules/node-scripts.config.js`; the `name`, `main` or `dependencies` of a module `package.json`; `bnd.bnd` `Web-ContextPath` of a module that has JS; files under `src/main/resources/META-INF/resources/js/api/`; `*JSImportMapsContributor.java` / `*DynamicJSImportMapsContributor.java`; `modules/frontend-sdk/node-scripts/util/esbuild/**`, `util/amd/**`, `util/configuration/**`; `frontend-js-importmaps-extender*`, `frontend-js-loader-modules-extender*`. Code signals: `import … from '<other-module>'` or `'<other-module>/<path>'`, relative imports climbing out of the module (`../../../../<other-module>/src/...`), `module="{X} from <context>"` in JSPs, `FrontendESMUtil.buildURL(`, `ESImportUtil`, `forESModule(`, `Liferay.Loader.require`, `Liferay.Loader.define`, `__liferay__/`, `eslint-disable … no-cross-module-deep-import`.

## What the reviewer needs to know

### The build links modules, the browser loads ES modules

- Portal JS is built per OSGi module by `@liferay/node-scripts` (`modules/frontend-sdk/node-scripts`, `"build": "node-scripts build"`) with esbuild, as **ES modules**. The old liferay-npm-bundler / AMD pipeline is gone from portal modules. There are 315 `node-scripts.config.js` files, no `liferay-npm-bundler.config.js` or `npmscripts.config.js`, and `.npmbundlerrc` only appears in Gradle workspace plugin test fixtures (`git ls-files '*.npmbundlerrc'`).
- Each module produces one ESM bundle per entry point (`main` → `__liferay__/index.js`, each submodule → `__liferay__/<name>.js`). Each third-party package the module exports gets its own `__liferay__/exports/<flat-name>.js` (`util/esbuild/util/getURL.mjs`). Code splitting is off, so every entry point is self-contained (`util/esbuild/bundleJavaScriptMain.mjs`).
- **Cross-module imports are resolved at build time, not at runtime.** `util/esbuild/plugins/getLinkerPlugin.mjs:99-201` looks the import specifier up in the generated global map `modules/node-scripts.config.js`:
  - `'<pkg-name>'` of another module → external URL `../../<web-context>/__liferay__/index.js`.
  - `'<pkg-name>/<submodule>'` → external URL `…/__liferay__/<submodule>.js`.
  - a third-party package that some module lists in `exports` → an import bridge re-exporting `…/<provider-context>/__liferay__/exports/<pkg>.js`.
  - `*.css` that a provider exports → a CSS loader module.
  - anything else → **bundled into the importing module** (normal esbuild resolution).
- The global map is generated from every module's `node-scripts.config.js` (`util/createGlobalConfig.mjs`). Every buildable module (one that has a `node-scripts.config.js`) appears in it under its `package.json` `name`, with its `exports` and `./<submodule>` entries. **Any module with a `main` can be imported by other modules through its package name.** Running `node-scripts format` from `modules/` rewrites the file whenever a `node-scripts.config.js` changes (`util/format/formatters/formatGlobalNodeScriptsConfig.mjs`), and `checkFormat` fails if it is stale.
- The URL is computed from the package name, not from `bnd.bnd`: `@liferay/` is stripped and the rest is used as the web context path (`util/configuration/getGlobalImports.mjs:58`). The comment there admits nothing enforces that the two match.
- **Import maps** (`frontend-js-importmaps-extender`, which prints `<script type="importmap">` at `top_head.jsp#pre`, `JSImportMapsExtenderTopHeadDynamicInclude.java:55`) are for code that is **not** built by node-scripts: client extensions, fragments, and inline module scripts. Contributors are `JSImportMapsContributor` / `DynamicJSImportMapsContributor` services. Examples: `FrontendJSReactWebDynamicJSImportMapsContributor` (react, react-dom…), `FrontendJSDependenciesWebDynamicJSImportMapsContributor` (`@liferay/frontend-js-api`), `FDSDynamicJSImportMapsContributor` (`@liferay/frontend-data-set-web/api`), `ClientExtensionJSImportMapsContributor`. Every import-map entry is a public contract with code Liferay does not control.
- **AMD is legacy compatibility only.** For each module with a `main` or `exports`, node-scripts still writes AMD bridges (`util/amd/writeMainBridge.mjs:42` `Liferay.Loader.define("<name>@<version>/index", …)` re-exporting the ESM), a `manifest.json` and a `package.json`, so `frontend-js-loader-modules-extender` can serve `Liferay.Loader.require('<name>@<version>/index')`. Portal itself barely uses it (2 calls: `frontend-js-web/.../liferay/lazy_load.js:47`, `.../utils/client_extensions/loadModule.ts:50`). No JSP uses `<aui:script require=…>` any more.
- **From JSP/Java**, ES modules are referenced as `module="{Symbol} from <web-context>[/<submodule>]"` in `<react:component>` / `<liferay-frontend:component>` (hundreds of JSPs; none still uses a bare AMD module name), or with explicit URLs `FrontendESMUtil.buildURL(themeDisplay, "<web-context>", "<submodule>")` in `<aui:script type="module">`. The part after `from` is the **web context path** (bnd `Web-ContextPath` without the slash), not the npm name: `ESImportUtil._getURL` (`frontend-js-loader-modules-extender-api/.../esm/ESImportUtil.java:83`) splits on the first `/` and builds `/o/<context>/__liferay__/<path>.js`.

### What makes a module importable (its public API)

`node-scripts.config.js` (the old `package.json`-only model is outdated):

```js
module.exports = {
	main: './src/main/resources/META-INF/resources/index.ts', // public entry, named exports only
	submodules: {                                              // optional extra public entry points
		api: './src/main/resources/META-INF/resources/js/api/api.ts',
	},
	exports: ['some-npm-package', 'some-npm-package/sub/path', 'pkg/dist/x.css'], // re-share 3rd-party pkgs
	symbols: {'some-npm-package': ['default', 'foo']}, // override inferred export names (only for own `exports`)
	typescript: {main: './src/main/resources/META-INF/resources/index.d.ts'},   // types entry if different
};
```

- `main` and submodule paths must be under `./src/main/resources/META-INF/resources/` (or end in `/src/index.ts`), or the build throws (`util/configuration/getProjectEntryPoints.mjs:75`).
- `package.json` `main` (relative to `META-INF/resources`) must point to an existing file that has no `export default` (`util/format/formatters/formatPackageJSONFiles.mjs:161`, "use named exports only"). `@liferay/portal/no-default-export-from-frontend-js-web` enforces the same idea for consumers of `frontend-js-web`.
- `symbols` may only name packages the module itself `exports` (`util/createGlobalConfig.mjs:34`). Overrides are exhaustive (see the comment block in `modules/node-scripts.config.js`).
- **`api` submodule convention**: a submodule named `api` must live at `…/resources/js/api/api.{js,ts}` (`formatAPISubmodules.mjs`). Files there may not import relative paths outside `js/api/` (`@liferay/portal/no-api-submodule-import`, enabled in `plugin:@liferay/portal`). Static import-map entries contributed from Java must be named `…/api` and point to `__liferay__/api.js` or `__liferay__/exports/…` (source-formatter `JavaJSImportMapsContributorCheck.java:55`). Current `api` submodules: `@liferay/fragment-impl`, `@liferay/frontend-data-set-web`, `dynamic-data-mapping-form-field-type`.
- Deep imports into another module are blocked by `@liferay/portal/no-cross-module-deep-import` (`modules/.eslintrc.js:81`, configured with the global map). Importing `'<module>/<x>'` fails unless `<x>` is a declared submodule or export.
- Third-party packages are shared by one **provider** module listing them in `exports`. Main providers: `frontend-js-dependencies-web` (generic libraries, `@liferay/js-api`), `@liferay/frontend-js-react-web` (React family, formik, classnames, prop-types), `@liferay/frontend-js-clay-web` (`@clayui/*`, Clay CSS), `frontend-editor-ckeditor-web` (CKEditor 5, CodeMirror 6), `frontend-js-recharts`, `@liferay/frontend-js-codemirror-web`.

## Review checklist

- **New or changed `main`/`submodules`/`exports` = new public API.** Once another module, a JSP `module="{X} from …"`, an AMD consumer or (through an import map) a client extension uses it, removing or renaming it is a breaking change. Ask: who consumes this? Is it meant to be public? Is the exported name final? Prefer adding to an existing `api` submodule over exposing internals from `main`. The old guideline's "once you export something you can never remove it" still holds.
- **Import-map additions (`*JSImportMapsContributor.java`)** make an API public to client extensions. Check the name ends in `/api` (or is a shared third-party export), that it points to `__liferay__/api.js` or `__liferay__/exports/…`, and that someone (the owning team plus Frontend Infra) accepts the compatibility obligation.
- **Deep or relative imports into another module** (`'../../../../other-module/src/…'`, `'@liferay/x/some/file'`) bundle a private copy of that code into the importer. Singletons (`@liferay/frontend-js-state-web` atoms, React contexts, event buses, caches) then exist twice and silently diverge. Ask the author to import the provider's public entry point instead, or to have the provider expose a submodule. Challenge any new `eslint-disable-next-line @liferay/portal/no-cross-module-deep-import` outside tests. All 52 in master are in tests (51 for `@liferay/layout-js-components-web/test/__lib__/index`, 1 relative import of `frontend-js-state-web` source in `frontend-data-set-web/test/js/api/FDSConnection.ts:13`).
- **Importing a third-party package that another module already provides**: the consumer must not bundle its own copy. If the specifier differs from what the provider exports (e.g. a subpath `pkg/lib/x`), it is bundled instead of linked. Ask the author to use the exported specifier, or to add the subpath to the provider's `exports`.
- **Adding a package to a provider's `exports`** changes what every module and client extension gets at runtime. Ask for a version-compatibility check of all current consumers and a regenerated `modules/node-scripts.config.js`. Ask for a `symbols` entry when the package is browser/server polymorphic or has no inferable named exports (comment block in `modules/node-scripts.config.js`).
- **`package.json` `name` vs `bnd.bnd` `Web-ContextPath`** must match (minus `@liferay/`) for any module others import. Otherwise the linker emits URLs to the wrong context. Master already has mismatches, e.g. `product-navigation-product-menu-web` is named `product-navigation-control-menu-web`, and `site-memberships-web` is named `site-membership-web`. Importing those by name would 404 or hit the wrong bundle. New modules should not add more.
- **Edits to `modules/node-scripts.config.js` by hand**: it is generated ("AUTO-GENERATED: DO NOT EDIT"). The diff must come from `node-scripts format` run in `modules/`, and match the per-module config changes in the same PR.
- **JSP `module="{X} from <name>"`**: `<name>` must be the web context path, and `X` must be a named export of that module's `main` (or of the submodule after `/`). An `@liferay/…` npm name there breaks the URL.
- **Files shared between `main` and a submodule** of the same module: an import that crosses submodule boundaries is linked to the other submodule's URL. A file outside every submodule folder is duplicated into each bundle and triggers a build warning (`util/esbuild/util/CrossSubmoduleImportsChecker.mjs:83`). Ask for the shared file to go under one submodule.
- **New AMD usage** (`Liferay.Loader.define/require`, manual `manifest.json`): ask why ESM is not enough. Only legacy/third-party interop needs it.
- **Changes to `getLinkerPlugin.mjs`, `createGlobalConfig.mjs`, `getGlobalImports.mjs`, AMD bridge writers**: these affect every module. Ask for a full build and a smoke test of pages that mix many modules (Page Editor, Data Sets, CKEditor), plus a client extension that uses the import map.

## Use cases and how-tos

- **Consume another module's API**: add `"<pkg-name>": "*"` to `dependencies` in your `package.json` (source-formatter forces `*` for internal modules, `JSONPackageJSONDependencyVersionCheck.java:170`). Then `import {x} from '<pkg-name>'` or `'<pkg-name>/<submodule>'`.
- **Expose a function to other modules**: export it (named) from `main`, or from a submodule declared in `submodules`. For something client extensions should use, create the `api` submodule at `js/api/api.ts` and, if needed, an import-map contributor named `<pkg>/api`.
- **Use a shared third-party library**: declare it in your `package.json` `dependencies` at exactly the provider's version and import it normally. The build links it to the provider. See `npm-packages-and-dependencies.md` for adding a library nobody provides yet.
- **Reference a module from JSP**: `<react:component module="{MyComponent} from my-module-web" props="<%= … %>" />`, or in `<aui:script type="module">` use `import {x} from '<%= FrontendESMUtil.buildURL(themeDisplay, "my-module-web", "submodule") %>';`.
- **Diagnose a runtime "does not provide an export named X"** for a linked third-party package: check `symbols` overrides in the provider's `node-scripts.config.js`. Inferred symbols come from requiring the package in Node, which can differ from its browser build.

## Pitfalls and side effects

- Bundling instead of linking is silent. A typo in a specifier, or a subpath the provider does not export, still builds. It just ships a second copy. `CREATE_BUNDLE_REPORTS=yes` plus `node-scripts report:bundle-imports` / `report:dependencies` show what each bundle linked or inlined.
- Imports "jump" into the provider's bundle. Code inside a linked package runs with the provider's dependency graph, not the importer's (the old bundler had the same behavior). Version alignment is enforced on `package.json` (`formatPackageJSONVersionAlignment.mjs`), so build-time and runtime versions agree.
- Renaming a module's `package.json` `name` breaks every importer and every AMD consumer of `<name>@<version>/index`. Changing `Web-ContextPath` breaks every JSP `module="… from <context>"` and every `FrontendESMUtil.buildURL` call.
- Removing a module from the yarn workspace globs, or moving it, removes it from the global map. Importers then bundle nothing and fail to resolve, and the `EXPECTED_YARN_WORKSPACE_PROJECTS.mjs` snapshot check fails.
- `exports` of CSS (`'@clayui/css/lib/css/atlas.css'`, `'pkg/x.css'`) are served by the provider. Importing them elsewhere yields a loader stub, not inlined CSS.

## Not carried over

- Import sorting, grouping, blank-line and `require()` placement rules (`guidelines/general/imports.md`: Sorting, Grouping, Other lints, `require()` vs `import`): code shape, enforced by `@liferay/sort-imports`, `@liferay/group-imports`, `@liferay/imports-first`, `@liferay/no-duplicate-imports`, `@liferay/destructure-requires`, `@liferay/no-absolute-import`, `@liferay/no-dynamic-require`, `@liferay/no-require-and-call` in `modules/frontend-sdk/eslint-plugin/rules/general/`. The only functional point kept: side-effect-only imports (`import './x.scss'`) form a barrier the sorter will not reorder across, and `@liferay/portal/no-loader-import-specifier` requires SCSS to be imported for side effects only.
- Bundler v2 versioning strategies (same / different / omitted version in `package.json` vs `.npmbundlerrc`), the `billboard.js` / `frontend-taglib-clay` Slack Q&A, nested `.npmbundlerrc` semantics, `liferay-npm-bundler-preset-liferay-dev` default imports: obsolete with the removal of the bundler from portal (evidence above).
- `scripts` block example with `liferay-npm-scripts build/check/fix` (`guidelines/dxp/exporting.md`): obsolete. Scripts are now `node-scripts build`, `node-scripts format --check`, `node-scripts format`, enforced by source-formatter `JSONPackageJSONCheck`.
- Links to `liferay-frontend-guidelines` / `liferay-npm-tools` repos: dead or moved.
