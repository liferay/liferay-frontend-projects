# Glossary

<!-- Sources: guidelines/general/glossary.md -->

**Applies when the PR touches:** documentation, `README`/`AGENTS.md` files, JSDoc, PR descriptions, language keys or error messages that name frontend artifacts; also use it to read review comments consistently. This is terminology, not a code check.

## What the reviewer needs to know

Words like *module*, *package* and *bundle* mean different things in the frontend and the backend. Use the qualified term whenever context does not make it obvious. Terms below have been checked against master.

### Frontend

- **JavaScript module**: any JS module, whatever its format.
  - **ES module**: `import`/`export` syntax. Portal source is written as ES modules. `@liferay/node-scripts` bundles them with esbuild (`modules/frontend-sdk/node-scripts/bundle/index.mjs`), and they are served under `/o/<web-context-path>/__liferay__/…` (comment in `modules/frontend-sdk/node-scripts/util/amd/writeMainBridge.mjs`). Imports between portal modules are rewritten at build time into external `/o/<web-context>/__liferay__/…` URLs (`node-scripts/util/esbuild/plugins/getLinkerPlugin.mjs`). Import maps (`modules/apps/frontend-js/frontend-js-importmaps-extender`) resolve bare specifiers only for code built outside portal, such as client extensions and fragments. Do not write "ESModule", "ECMAScript module" or "Harmony module".
  - **AMD module**: a module registered with `Liferay.Loader.define` and loaded through `Liferay.Loader.require`, served under `/o/js/resolved-module/…` by `frontend-js-loader-modules-extender`. New portal code does not produce AMD modules directly. See *AMD bridge*.
  - **CommonJS module**: `require`/`module.exports`. Node tooling (`*.js` in `@liferay/node-scripts` next to `*.mjs`) and the Jest transform (`@babel/plugin-transform-modules-commonjs` in `util/jest/getJestConfig.js`).
- **AMD bridge**: an AMD module generated by `@liferay/node-scripts` (`util/amd/writeMainBridge.mjs`, `writeExportBridges.mjs`) that re-exports an ES module, so code still using `Liferay.Loader.require('<pkg>@<version>/index')` gets the ESM build.
- **npm package**: anything described by a `package.json`. In portal every module with a `package.json` is also a yarn workspace project (`modules/package.json` `workspaces`).
- **`@liferay/node-scripts`**: the portal frontend toolchain (build, format, lint, test, preflight) at `modules/frontend-sdk/node-scripts`, called as `node-scripts <command>`. It replaced `@liferay/npm-scripts` inside portal.
- **`node-scripts.config.js`**: per-module build config (exports, `submodules`, …). `modules/node-scripts.config.js` is the **generated** global map built from all of them ("AUTO-GENERATED: DO NOT EDIT"). It is regenerated by `node-scripts format` run from `modules/` (`node-scripts/util/format/formatters/formatGlobalNodeScriptsConfig.mjs`). The `generate:global-config` command named in `node-scripts/AGENTS.md` does not exist in `bin.js`.
- **Feature flag**: a `feature.flag.<KEY>` portal property, checked with `FeatureFlagManagerUtil` in Java/JSP and with `Liferay.FeatureFlags['<KEY>']` in JS. Types are `dev`, `beta`, `release` and `deprecation` (`portal-kernel/.../feature/flag/FeatureFlagType.java`). See `review-process.md`.
- **Client extension (CX)**: a deployable extension described by a client extension type (`*CET` classes in `modules/apps/client-extension/client-extension-type-api/.../type/`, e.g. `GlobalJSCET`, `CustomElementCET`, `JSImportMapsEntryCET`, `FDSFilterCET`). `@liferay/js-api` (in liferay-frontend-projects, `client-extensions/js-api`) is the "public Liferay DXP API to be used from Client Extensions".
- **`Liferay` global object**: the `window.Liferay` object rendered server-side, partly by `frontend-js-web`'s `LiferayGlobalObjectPreAUIDynamicInclude` (it includes `FeatureFlags`, `Language`, …). In Jest it is replaced by `modules/frontend-sdk/node-scripts/util/jest/mocks/Liferay.js`.

### Backend

- **Java package**: a Java language package.
- **OSGi bundle**: the deployed JAR (or its runtime `org.osgi.framework.Bundle`).
- **OSGi module**: the source project of an OSGi bundle. People also use it for the bundle itself, which is acceptable, but prefer *OSGi bundle* for the JAR.
- **Portlet**: a UI unit managed by DXP, deployed inside an OSGi bundle. **Widget** is the user-facing synonym.

### Ambiguous terms

- **Module**: only when context makes clear it means a JavaScript module or an OSGi module. In portal reviews "module" usually means the OSGi module directory (`modules/apps/...`), which is often also an npm package. Qualify it when that matters.
- **Package**: a Java package or an npm package. Qualify it.
- **Bundle**: an OSGi bundle, or the output of a JS bundler (esbuild). Qualify it.

## Review checklist

- **Qualified terms in docs and PR descriptions** — "the module" in a frontend infra PR can mean the OSGi module, the npm package or a JS file. Ask for the qualified term when the ambiguity hides something (e.g. "exported from the module" — which entry point?).
- **No new references to deprecated tooling** — docs or READMEs that tell readers to use `liferay-npm-bundler`, `liferay-npm-scripts` or webpack for portal modules are outdated. Point them to `@liferay/node-scripts`.
