**Applies when the PR touches:** any `package.json` under `modules/` (sections `dependencies`, `devDependencies`, `resolutions`, `workspaces`, `name`, `private`); `modules/package.json`; `modules/yarn.lock`; `modules/.yarnrc`; `node-scripts.config.js` `exports`; `modules/frontend-sdk/node-scripts/util/format/formatters/ALLOWED_*.mjs`, `EXPECTED_YARN_WORKSPACE_PROJECTS.mjs`, `FORBIDDEN_ROOT_PACKAGE_JSON_SECTIONS.mjs`, `formatPackageJSON*.mjs`, the `ALLOWED_NON_GLOBAL_DEPENDENCIES` / `ALLOWED_NAMED_SCOPE_EXCEPTIONS` lists in `formatPackageJSONFiles.mjs`; `source-formatter-suppressions.xml` entries for `JSONPackageJSONCheck`; a new directory with a `package.json` (new module or new npm package). In liferay-frontend-projects: `projects/**/package.json`, `client-extensions/**/package.json`, `.yarnrc`, `yarn.lock`, `package-lock.json`, `.github/workflows/*`. Code signals: `"npm:<pkg>@<ver>"` aliases, version ranges (`^`, `~`, `>=`), `"resolutions"`, `"private": true`, `postversion`/`liferay-js-publish`, `npm publish`.

## What the reviewer needs to know

### How npm dependencies work in liferay-portal master

- **One Yarn v1 workspace.** `modules/package.json` declares `workspaces` (`apps/*/*`, `apps/*/*/*`, `dxp/apps/*/*`, `frontend-sdk/*`, Clay packages, playwright, …). There is one `modules/yarn.lock` ("yarn lockfile v1"), and `modules/.yarnrc` points to an offline mirror `./node_modules_cache` (not committed). Developers do not run yarn directly; Gradle (`yarnInstall`, `packageRunBuild`, `packageRunFormat`) does. Only `modules/package.json` may declare `workspaces` (`formatPackageJSONForbidNestedWorkspaces.mjs`).
- **Exact versions everywhere.** `dependencies`/`devDependencies` must use explicit versions. `^`, `~`, `<`, `>`, `|`, spaces and leading `=` are rejected (`formatPackageJSONExplicitVersions.mjs:10`). The only exception is `@clayui/*` (`ALLOWED_RANGE_VERSIONED_PACKAGES.mjs`). Internal workspace modules are referenced as `"*"`, and source-formatter rewrites them to `*` (`JSONPackageJSONDependencyVersionCheck.java:170`). It also forces React-family versions to match `frontend-js-react-web/package.json` and `@clayui/*` to match `frontend-js-clay-web/package.json`.
- **One version per package across the repo.** Every `package.json` must use the same version string for a given dependency (`formatPackageJSONVersionAlignment.mjs:92` "has misaligned versions across modules"). Divergences are allowlisted per project in `ALLOWED_PACKAGE_VERSION_DIVERGENCES.mjs`: currently only `@liferay/prettier-plugin`, `@types/node` and `typescript`, for externally consumed REST clients and `prettier-config`. Upgrading a library therefore means changing it in every `package.json` that lists it, in one PR.
- **Runtime dependencies must come from a provider module.** Each entry in a module's `dependencies` must be either another workspace module or a package some module lists in its `node-scripts.config.js` `exports`. Otherwise `checkFormat` fails with "Dependency 'x' is not provided by a specific module (see LPS-168443)" (`formatPackageJSONFiles.mjs:102`). Legacy exceptions live in `ALLOWED_NON_GLOBAL_DEPENDENCIES` (`formatPackageJSONFiles.mjs:443`: CKEditor 5 packages, `@fullcalendar/*`, `d3`, `leaflet`, `lodash`, `monaco-editor`, `graphiql`, `recharts`, polyfills, …). Those packages get **bundled into the consuming module**. Why this matters at runtime is in `module-imports-and-exports.md`.
- **`devDependencies` are effectively not allowed in module `package.json`.** Source-formatter `JSONPackageJSONCheck.java:69` reports `Entry "devDependencies" is not allowed` for `modules/apps|dxp/apps|private/apps/**/package.json` with a `bnd.bnd`/`build.gradle`. Exceptions are suppressed per file (`analytics-client-js`, `frontend-js-react-web`, `frontend-js-clay-web`, several commerce modules: `source-formatter-suppressions.xml:192,196`, `modules/apps/commerce/source-formatter-suppressions.xml`). Test tooling (Jest, Testing Library, jest-axe, fetch mocks) is provided by `@liferay/node-scripts` itself (`modules/frontend-sdk/node-scripts/package.json`). That is why `modules/.eslintrc.js:61` allowlists `@testing-library/*` in `@liferay/no-extraneous-dependencies`.
- **Root `modules/package.json` is locked down.** No `dependencies` section (`FORBIDDEN_ROOT_PACKAGE_JSON_SECTIONS.mjs`). `devDependencies` only for `@types/*`, allowlisted divergences and `ALLOWED_ROOT_PACKAGE_JSON_DEPENDENCIES.mjs` (`eslint-plugin-react-compiler`, `jsdoc`, each with a written reason). `@types/*` may live **only** in the root (`formatPackageJSONTypesLocation.mjs`). `resolutions` must be selective (`parent/**/child`, not `child`) and documented in `ALLOWED_ROOT_PACKAGE_JSON_RESOLUTIONS.mjs` (currently empty) (`formatGlobalPackageJSONResolutions.mjs`).
- **Lockfile guard**: `formatYarnLock.mjs` rejects `resolved` URLs on `localhost`/`127.0.0.1`. Today all 1608 entries resolve to `https://registry.yarnpkg.com`.
- **Workspace snapshot**: adding, removing or renaming a workspace project fails `formatYarnWorkspaceProjects.mjs` until `EXPECTED_YARN_WORKSPACE_PROJECTS.mjs` is updated. This is a deliberate review gate for new npm projects in portal.
- **Scoped names (dependency-confusion mitigation)**: every `package.json` `name` must start with `@liferay/` unless it is in the frozen legacy list `ALLOWED_NAMED_SCOPE_EXCEPTIONS` (`formatPackageJSONFiles.mjs:86,197`). `alloy-ui` may only be declared by 3 projects (`ALLOWED_AUI_DEPENDENT_PROJECTS.mjs`). Source-formatter `JSONDeprecatedPackagesCheck` bans `@clayui/checkbox`, `liferay-module-config-generator` and `metal-cli` (`sourcechecks.xml:1241`).
- **Where these checks run**: the portal-wide policies above run only when `node-scripts format [--check]` is invoked **from `modules/`** (`format/index.mjs` → `formatPortal.mjs`), e.g. `checkFormat` = `node-scripts format --check --current-branch` in `modules/package.json`. Running format inside a single module only formats and lints its files (`formatProject.mjs`). `gradlew checkSourceFormatting` / `formatSource` is finalized by `packageRunCheckFormat` / `packageRunFormat` (`SourceFormatterDefaultsPlugin.java:113,135`).
- **Ownership**: `modules/frontend-sdk/` is owned by `@liferay-frontend` (`.github/CODEOWNERS:474`), so edits to the allowlists above need Frontend Infra approval. `modules/package.json` and `modules/yarn.lock` have no explicit owner.

### npm packages published from liferay-frontend-projects

- Active published packages: `projects/eslint-plugin`, `prettier-config`, `prettier-plugin`, `stylelint-plugin`, `js-toolkit`, `js-themes-toolkit`, `npm-tools/packages/{changelog-generator,jest-junit-reporter,js-publish,npm-scripts}`, `client-extensions/js-api` (`@liferay/js-api`), plus `maintenance/` branches.
- Typical release wiring: `preversion` runs checks, `postversion: npx liferay-js-publish` (prompts for OTP, `projects/npm-tools/packages/js-publish/src/index.js:205`). Changelogs come from `liferay-changelog-generator`, run with `npx` and configured with a `.yarnrc` `version-tag-prefix` (`<pkg>/v`). `@liferay/js-api` instead uses npm (`package-lock.json`) and `postversion: git push upstream --follow-tags && npm publish`.
- PR titles are validated as Conventional Commits by `.github/workflows/conventional-commits.yml` (`amannn/action-semantic-pull-request`). Lockfile drift is checked by `.github/workflows/lockfile.yml` (`git diff --quiet -- yarn.lock`). Dependabot runs weekly with a limit of 1 open PR (`.github/dependabot.yml`).
- Portal no longer consumes `@liferay/npm-scripts`. It has its own in-tree toolchain (`modules/frontend-sdk/node-scripts`, `@liferay/node-scripts` 1.0.0, unpublished) and in-tree copies of `@liferay/eslint-plugin`, `@liferay/prettier-plugin`, `@liferay/prettier-config` and `@liferay/stylelint-plugin` under `modules/frontend-sdk/`. Those copies are workspace packages that portal resolves locally, and they have diverged from this repo (`diff -rq projects/eslint-plugin …/frontend-sdk/eslint-plugin`).

## Review checklist

- **New third-party runtime dependency in a portal module** — ask: is it already provided (`grep` `modules/node-scripts.config.js`)? If yes, use the same exact version and import it, and do not bundle a copy. If not, the standard path is to add it to the right provider's `package.json` + `exports` (usually `frontend-js-dependencies-web`, React-related ones to `frontend-js-react-web`). Adding it to `ALLOWED_NON_GLOBAL_DEPENDENCIES` means every consumer bundles its own copy, and needs a justification (single consumer, huge, or not ESM-safe).
- **Is the package worth it?** Each dependency is a permanent cost (audits, upgrades, bundle size, CSP/security review, transitive graph). Ask for size (`report:bundle-sizes`), transitive count (`yarn why`), maintenance status, and whether a few lines of code or an existing provider package would do. The old guideline's "think carefully before adding a dependency" still applies.
- **License / OSS compliance** — ask which license the package and its new transitive deps use, and whether it is on the approved list. Copyleft (GPL/AGPL) or unknown licenses are blockers until Legal clears them. No automated license check exists in node-scripts (see flag).
- **Version bump of a shared package** — every module importing it runs the new version, and so does every client extension if it is import-mapped. Ask for the changelog review (breaking changes, browser support, ESM/CJS shape changes that may need `symbols` overrides), a full `modules/` build, and tests of the main consumers. All `package.json` copies must be bumped together (alignment check).
- **Ranges, `resolutions`, `npm:` aliases** — ranges fail the check except Clay. `resolutions` must be selective and documented with a reason. An `npm:<pkg>@<ver>` alias (as used for `react-16`, `react-18`, `@testing-library/*-<ver>`) creates a second copy on purpose. Ask why, and whether it must be exported for runtime or is test-only.
- **Lockfile-only diffs** (`modules/yarn.lock` changes without a matching `package.json` change) — ask why. Lockfile pins do not reach consumers, are easily reverted by the next install, and hide intent. For a transitive security fix, prefer bumping the direct dependency that pulls it in. Use a documented selective resolution only as a last resort.
- **Security advisories (Dependabot / `yarn audit`)** — triage impact (runtime vs build-only, exposure to untrusted input) before rushing a merge. Batch non-critical updates, and treat critical runtime ones as urgent.
- **New module / new `package.json` in portal** — name it `@liferay/<bundle-name>` and make it match `Web-ContextPath`. Do not add it to `ALLOWED_NAMED_SCOPE_EXCEPTIONS`. Update `EXPECTED_YARN_WORKSPACE_PROJECTS.mjs`. Place it inside the workspace globs so `"*"` resolves locally. `"private": true` does not protect an unpublished unscoped name.
- **Edits to `modules/frontend-sdk/node-scripts/util/format/formatters/ALLOWED_*.mjs` / suppressions** — each widening of an allowlist (divergences, root deps, range packages, AUI dependents, named-scope exceptions, non-global deps, `JSONPackageJSONCheck` suppressions) needs a written reason in the file and Frontend Infra sign-off. Changing node-scripts also requires its `com.liferay.sha256` hash to be updated (`formatNodeScriptsHash.mjs`).
- **Creating a new npm package** (in portal or in liferay-frontend-projects) — challenge it first. Can it live inside an existing module or package? Real reuse in several places, or a third-party plug-in contract (ESLint, Babel, Prettier), justifies it. "Might be reusable" does not. If it is accepted, check the publishing checklist under use cases.
- **Publishing credentials** — packages must be published to the `@liferay` scope by the shared `liferay` npm org/team, with 2FA. Not from personal scopes or forks.

## Use cases and how-tos

- **Use a library another module already provides** (e.g. `date-fns`): add `"date-fns": "<same version as frontend-js-dependencies-web>"` to `dependencies` and import it. The build links it to `frontend-js-dependencies-web`.
- **Add a new shared library**: (1) add it with an exact version to the provider's `package.json` `dependencies` and to its `node-scripts.config.js` `exports` (plus `symbols` if Node-side export inference is wrong); (2) add the same version to each consumer's `dependencies`; (3) run `node-scripts format` in `modules/` to regenerate `modules/node-scripts.config.js` and run the policy checks; (4) commit `yarn.lock`; (5) consider an import-map contributor only if client extensions must share it.
- **Add types for a library**: add `@types/<pkg>` at an exact version to `modules/package.json` `devDependencies`, never to the module.
- **Force a transitive version**: prefer upgrading the parent. Otherwise add a selective resolution `parent/**/child` to `modules/package.json` and a reason to `ALLOWED_ROOT_PACKAGE_JSON_RESOLUTIONS.mjs`.
- **Publish a new package from liferay-frontend-projects** (checklist distilled from the old guideline; current examples: `projects/eslint-plugin`, `client-extensions/js-api`): approved proposal (issue in liferay-frontend-projects); lives under the `liferay` GitHub org in this monorepo; `@liferay/` scoped name; `license` and SPDX headers (`copyright.js`, `LICENSES/`); `format`/`format:check`, `lint`/`lint:fix`, `test` and `ci` scripts; `preversion` runs `ci`; `postversion` publishes (`liferay-js-publish` or `npm publish`); `.yarnrc` with `version-tag-prefix "<pkg>/v"` for changelog tags; README, CONTRIBUTING with release steps, CHANGELOG; after the first publish, give access to the `liferay` org team.

## Pitfalls and side effects

- Adding a package to `dependencies` of one module without a provider fails `checkFormat` only when the check runs from `modules/`. A module-local `yarn format` passes, so authors may not notice before CI.
- The alignment check makes "upgrade only my module" impossible by design. A PR that bumps a library in one `package.json` but not in the others fails, and a PR that bumps all of them changes runtime for everyone.
- Bundled (non-provided) packages are duplicated per consumer. Two modules bundling `lodash` or `leaflet` ship two copies, and any package with global state (polyfills, `core-js`, singletons) can conflict.
- Moving a module out of the workspace globs makes `"*"` dependencies on it resolve against the public registry. That is the dependency-confusion scenario, and it is also caught by the workspace snapshot.
- `"private": true` only prevents publishing. It does not stop `npm install` from fetching a same-named package from the registry.
- Changing `modules/frontend-sdk/node-scripts/package.json` dependencies changes the toolchain of every module (build, lint and test).
