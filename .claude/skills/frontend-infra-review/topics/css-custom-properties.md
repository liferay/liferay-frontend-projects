# CSS custom properties, frontend tokens and style books

<!-- Sources: guidelines/dxp/how_to_use_css_custom_properties.md -->

**Applies when the PR touches:** any `frontend-token-definition.json` (`modules/apps/frontend-theme/*/src/WEB-INF/`, `modules/apps/frontend-js/frontend-js-clay-web/src/main/resources/WEB-INF/`, Theme CSS client extensions under `workspaces/**/client-extensions/*/src/`), `modules/apps/frontend-token/**`, `modules/apps/frontend-css/frontend-css-variables-{api,web}/**`, `modules/apps/style-book/**`, `frontend-theme-*/src/css/custom_properties/**`, `frontend-theme-dialect/src/css/dialect/_classic_style_book_compat.scss`, `clay-css/src/scss/atlas-custom-properties/**`, `clay-css/src/scss/cadmin/variables/_c-root.scss`, `layout-api/.../CommonStylesUtil.java`, and any `.scss`/`.css` that adds, renames or removes a `--custom-property` or changes a `var(--...)` reference. Code signals: `var(--`, `light-dark(`, `$c-root`, `$cadmin-c-root`, `$cadmin-c-dark`, `cssVariable`, `cssVariableMapping`, `frontendTokensValues`, `FrontendTokenDefinitionRegistry`, `ScopedCSSVariablesProvider`, `data-color-scheme`, `LPD-57922`, `LPD-84497`, `liferay/no-hardcoded-colors`.

## What the reviewer needs to know

### Where custom properties come from

1. **Clay "custom properties" flavor** (`clay-css/src/scss/_atlas-custom-properties.scss`). The `$c-root` map (`atlas-custom-properties/variables/_c-root.scss`, about 520 properties) is written to `:root`. Values use `light-dark(light, dark)`, and the map sets `color-scheme: light`. Sass variables point at them (`$primary: var(--primary)`, `atlas-custom-properties/variables/_globals.scss:187`). Used by the **Prism** and **CMS** themes (`src/css/clay.scss`).
2. **Classic / Dialect**: Clay Atlas compiled with plain Sass values, then `src/css/custom_properties/_custom_properties_set.scss` reads custom properties with Sass fallbacks, e.g. `background-color: var(--body-bg, $body-bg)` and `padding-bottom: var(--aspect-ratio-4-to-3, 75%)`. Dialect defines Classic's names as aliases of its own tokens in `dialect/_classic_style_book_compat.scss` (`--primary: var(--color-brand-primary)`, ...). That is the existing pattern for keeping old variable names working.
3. **cadmin (admin UI on site pages)**: `$cadmin-c-root` / `$cadmin-c-dark` / `$cadmin-c-high-contrast` (`clay-css/src/scss/cadmin/variables/_c-root.scss`, `cadmin/components/_root.scss`) are written as `--cadmin-*` under `html:not(#__):not(#___):root .cadmin`. There are variants for `[data-color-scheme='dark']`, `[data-prefers-contrast='more']`, `prefers-contrast: more` and `forced-colors`. Style books never set `--cadmin-*`, so admin UI does not take site styling.
4. **Frontend token definitions** (`WEB-INF/frontend-token-definition.json`). These are the tokens a style book can edit. The JSON schema is `frontend-token-definition-api/.../frontend-token-definition.schema.json`: categories → sets → tokens, with `name` (required), `type` (`Boolean|Integer|Number|String`), `defaultValue`, `editorType` (`ColorPicker|Length`), `label` (language key), `validValues`, and `mappings` (required, `[{type: "cssVariable", value: "<name without -->"}]`; only `cssVariable` is used, `FrontendTokenMapping.TYPE_CSS_VARIABLE`). Sources (`FrontendTokenDefinitionRegistryImpl.java`):
   - Theme bundles: a bundle with both `WEB-INF/liferay-look-and-feel.xml` and the JSON. Today that is Classic (274 tokens), Prism (274), Dialect (601) and CMS (116). The definition ID is the JS-safe theme ID (`classic_WAR_classictheme`, ...). Theme type is `bundle`, priority 300.
   - Global: a bundle with the JSON but no look-and-feel. Today that is only `frontend-js-clay-web` (129 Clay tokens such as `colorPrimary` → `--primary`). The definition ID is the bundle symbolic name, priority 100. These tokens appear only when feature flag **`LPD-84497`** ("Clay's Global Frontend Token Definitions", default `false`, `portal.properties:7087`) is on (`FrontendTokenDefinitionRegistryImpl.java:139-170`).
   - Theme CSS client extensions: `ThemeCSSCET.getFrontendTokenDefinitionJSON()`, keyed by the CET external reference code, validated against the schema at registration.
   - Custom tokens defined in a style book itself (`StyleBookEntryLocalServiceImpl.updateFrontendTokenDefinition`, definition ID `StyleBookConstants.FRONTEND_TOKEN_DEFINITION_ID_CUSTOM`, priority 500).

### How token values reach the page

- `ScopedCSSVariablesTopHeadDynamicInclude` (`frontend-css-variables-web`) writes one `<style data-senna-track="temporary">`. It contains every `ScopedCSSVariablesProvider` OSGi service (`frontend-css-variables-api`), ordered by `service.ranking`, each as `<scope> { --name: value; }`.
- `DefaultThemeScopedCSSVariablesProvider` (`frontend-token-definition-impl`, ranking `Integer.MAX_VALUE`, emitted first) writes the **defaults** of the layout's token definition at `:root`. The definition is resolved per layout in this order: Theme CSS CET on the layout, on the master layout, on the layout set, then the theme bundle.
- `StyleBookScopedCSSVariablesProvider` (`style-book-service`) then writes the layout's default **style book values** at `:root`, so they override the defaults. It writes nothing on control panel groups and layouts, or when `styleBookEntryPreview` is set (`StyleBookScopedCSSVariablesProvider.java:115-131`).
- When several definitions map to the same CSS variable, keys are sorted by priority (global 100 < theme/legacy 300 < custom 500) and the higher one wins (`_getSortedKeys`, `:138-180`).

### How style book values are stored (the compatibility contract)

- `StyleBookEntry.frontendTokensValues` is JSON keyed by `"<tokenDefinitionId>:<tokenName>"` (`FrontendTokensValuesUtil.getFrontendTokensValuesKey`). Each value is `{value, cssVariableMapping, tokenDefinitionId, name?}`. The style book editor (`style-book-web/.../style-book-editor/FrontendTokenSet.js:62-76`) **copies the CSS variable name into `cssVariableMapping` at save time**. When one token is linked to another, it stores `name` and a literal `value: "var(--<linked mapping>)"`.
- At render time `StyleBookScopedCSSVariablesProvider` uses the **stored** `cssVariableMapping`, not the current definition. A saved style book keeps emitting whatever variable name was current when it was saved.
- Style books are exported and imported with a `frontend-tokens-values.json` (`StyleBookEntryImpl.java:68,89`), and 19 such files are committed (site initializers, samples). Customer LARs and site initializers carry the same keys.
- Upgrade `style-book-service/.../upgrade/v1_10_0/StyleBookEntryFrontendTokensValuesUpgradeProcess.java` rewrote old un-namespaced keys to `<definitionId>:<name>`. That is the precedent for fixing stored values with an upgrade process.
- Page editor common styles store token names and render them as `var(--<cssVariable>)` (`layout-api/.../CommonStylesUtil.java:465-478`). Spacing renders as `var(--spacer-N, <rem>)` (`:486-498`). Fragment configuration fields bound to tokens render `var(--<mapping>)` (`FragmentEntryConfigurationParserImpl.java:415-426`). So the CSS variable names and the `--spacer-0..10` set are referenced from saved page data, not only from theme CSS.

### Dark/light mode and contrast

- Every bundled theme's `portal_normal.ftl` (and `_unstyled` `portal_pop_up.ftl`) sets `<html data-color-scheme="..." data-prefers-contrast="...">`. The color scheme comes from the session click `com_liferay_application_list_taglib_SideNavigationColorScheme` (default `light`), and contrast from `ACCESSIBILITY_SETTING_HIGH_CONTRAST` (`frontend-theme-classic/src/templates/portal_normal.ftl:5-10`). The user toggles it with `UnifiedSidebarColorSchemeButton.tsx` (`frontend-js-components-web`).
- Feature flag **`LPD-57922`** ("Dark and Light Mode", type `release`, default `false`) gates the experience. Prism declares it in `liferay-plugin-package.properties`.
- The stylelint rule `liferay/no-hardcoded-colors` (`modules/frontend-sdk/stylelint-plugin/rules/no-hardcoded-colors.js`) rejects hex/`rgb()`/`hsl()` literals outside `var()`, `light-dark()` and `url()`. Existing violations are baselined in `modules/frontend-sdk/node-scripts/util/format/stylelint/suppressed_errors.txt`. `node-scripts format` runs it, so new violations show up in CI. Do not comment on it by hand.

## Review checklist

- **Renaming or removing a CSS variable that a token maps to (`mappings[].value`)?** Saved style books keep emitting the old name, both in `cssVariableMapping` and in linked values `var(--old)`. Theme CSS that now reads only the new name silently loses every customer customization. Ask for one of these: keep the old variable as an alias (Dialect `_classic_style_book_compat.scss` pattern) or read both (`var(--new, var(--old))`), or add a `style-book-service` upgrade process that rewrites stored `frontendTokensValues` in `StyleBookEntry` **and** `StyleBookEntryVersion`. Also check committed `frontend-tokens-values.json` files.
- **Renaming a token `name`, a theme ID or a Theme CSS CET ERC?** They are part of the stored key `<definitionId>:<name>`. Existing values are orphaned and the style book editor shows defaults. Page editor common styles that stored the token name stop resolving (`CommonStylesUtil` falls back to the raw value). Ask for an upgrade process or a compatibility plan. (The `classic-2` → `prism` rename, LPD-92565, is the kind of change that needs this.)
- **Removing a token?** Saved values still render (the provider does not check the current definition), but nobody can edit them any more. Check whether anything still reads the variable, and whether CSS should keep a fallback.
- **Changing a `defaultValue`?** It changes every site using that theme that has not overridden the token, with no style book involved. Treat it as a visual change for all customers. In Prism, defaults are `var(--...)` / `light-dark(...)`, while Classic uses hex. Check that the value works in both color schemes.
- **New token?** Check that `label` is a real language key, `type` and `editorType` fit the value (`ColorPicker` for colors, `Length` for sizes), the mapped variable is actually consumed by the theme CSS (with a fallback in Classic-style themes), and the JSON validates against the schema. If the token belongs in both Classic and Prism (near-duplicates), ask whether both were updated.
- **Change to `frontend-js-clay-web/.../frontend-token-definition.json` (global Clay tokens)?** These map straight to Clay's `--primary`, `--secondary-d1`, ... used by Prism/CMS. They are behind `LPD-84497` today, but once released they become customer-saved state with the same compatibility rules.
- **New `ScopedCSSVariablesProvider`?** The `service.ranking` decides the order in the single `<style>` block, and later declarations at the same scope win. Ask which provider must override which, and whether the provider must skip the control panel like the style book one does.
- **Hardcoded colors in admin or Prism/CMS CSS?** Admin UI should use `var(--cadmin-*)`, and Prism/CMS should use Clay variables. Otherwise dark mode and high contrast break. Lint catches literals. Sass variables need a closer look. `$cadmin-*` color variables already resolve to `var(--cadmin-*)` (`clay-css/src/scss/cadmin/variables/_globals.scss:239-285`, e.g. `$cadmin-secondary-l3: var(--cadmin-secondary-l3)`), so they are dark-mode safe. Passing them to Sass color functions (`darken()`, `rgba($x, .5)`) breaks the build or the value. `atlas-variables` colors (`$gray-600`, `$primary` in module CSS) are literal hex and stay frozen at the light value.
- **Module CSS defining custom properties at `:root` or `body`?** The namespace is global and shared with themes, style books and customer CSS. Ask for scoping to the component root, or a clearly prefixed name, so it cannot collide with token-mapped names such as `--primary`, `--body-bg` or `--spacer-3`.
- **Changing `--spacer-*`, `--lfr-background-image-*` or other names emitted from Java (`CommonStylesUtil`)?** Those names are a contract between page editor saved data and theme CSS. Treat them as public API.

## Use cases and how-tos

- **Make module CSS follow the site theme and style book:** read the token-mapped variable with a fallback, e.g. `color: var(--brand-color-1, #{$primary});`. Do not hardcode or rely on the Sass variable alone.
- **Make admin UI follow dark mode and contrast:** scope under `html#{$cadmin-selector} .cadmin` and use `var(--cadmin-<name>)`. The values switch automatically with `data-color-scheme` / `data-prefers-contrast`.
- **Rename a token-mapped variable safely:** emit both names for at least one release, e.g. in the theme's `_custom_properties_set.scss` or a compat file: `:root { --old-name: var(--new-name); }` (or the reverse, depending on which one style books write). Plan an upgrade process to rewrite stored `cssVariableMapping` values.
- **Read or set a variable from JS:** `getComputedStyle(element).getPropertyValue('--x')` (inherited value) or `element.style.setProperty('--x', value)` (inline). The style book editor preview uses the latter on the preview root (`LayoutPreview.js:43`).
- **Customize from a customer theme or Theme CSS CET:** ship a `frontend-token-definition.json` with `cssVariable` mappings. Tokens appear in the style book editor for layouts using that theme or CET.

## Pitfalls and side effects

- Style book values are not applied in the control panel, but they are applied on site pages where admin UI also appears (control menu, product menu, page editor). That only stays safe because admin UI reads `--cadmin-*`, not the site token names. Admin CSS that reads `var(--primary)` will take the site's brand colors.
- `light-dark()` needs a `color-scheme` on an ancestor. Clay's `$c-root` sets `color-scheme: light`, and cadmin sets it per `data-color-scheme`. A component that sets `color-scheme` itself changes how every `light-dark()` value below it resolves.
- `DefaultThemeScopedCSSVariablesProvider` emits all defaults of the definition on every page: 601 declarations for Dialect. Adding many tokens grows every page's `<head>`.
- Global (Clay) definitions are filtered out unless `LPD-84497` is on, and `ThemeFactoryUtil` switches the default theme to Prism when `LPD-84497` or `LPD-57922` is on. Test token changes with the flags both on and off.
- Saved values may contain `var(--...)` references to other tokens (linked tokens). Removing the referenced variable breaks the dependent value even though its own key is unchanged.
