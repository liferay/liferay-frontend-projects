### How Gradle drives the build

- The `com.liferay.node` Gradle plugin adds `packageRunBuild`, which runs the `build` script of `package.json` (`NodePlugin.java:329-376`). If the script starts with `node-scripts`, Gradle first copies **the whole** `src/main/resources/META-INF/resources` into `build/node/packageRunBuild/resources` and then lets the build write its output there. `processResources` then merges that folder into the JAR (`NodePlugin.java:698-800`). So every non-entry file (legacy JS, JSP, images, and also the `.ts`/`.tsx` sources) ships as-is, next to the bundles.
- `modules/build.gradle:272-288` adds the module's `node-scripts.config.js`, the global `modules/node-scripts.config.js`, and (for modules with `.scss`) the Clay SCSS sources as `packageRunBuild` inputs. Changing the global config therefore invalidates every JS build. Master's `/pr-check` (`.claude/skills/pr-check/validations/portal/per-module-compile.md:63-71`) already widens the deploy set for this.
- `NODE_ENV` comes from the `nodejs.node.env` property (`NodeDefaultsPlugin.java:104-109` sets the env var whenever the property is non-empty). `build.properties:597` sets `nodejs.node.env=production`, and `build.properties:590` sets `nodejs.ci.node.env=production` for Jenkins (`LiferayCIPlugin.java:202-206`). Ant copies `nodejs.*` into `.gradle/gradle.properties` at `setup-sdk` time (`build-common.xml:2172,2235`). The task's environment is a Gradle `@Input` (`ExecuteNodeTask.java:114-117`), so changing `-Pnodejs.node.env` re-runs `packageRunBuild`.
- The `yarnInstall` at the root owns installs. A normal `deploy` never installs a newly added npm dependency, and `nodejs.yarn.install.frozen.lockfile=true` (`build.properties`) makes CI reject a `package.json` change without a matching `modules/yarn.lock` change. `/pr-check` checks the lockfile already (`per-module-compile.md:92-104`).

> **⚠️ REVIEW-FLAG [outdated]:** `NODE_ENV` no longer defaults to "production" when unset. Gradle builds are production only because `build.properties` sets `nodejs.node.env=production`. Running `yarn build` / `node-scripts build` straight from a shell with no `NODE_ENV` gives an **unminified, development** build (`minify: process.env.NODE_ENV === 'production'`, and esbuild then defines `process.env.NODE_ENV` as `"development"`). ### What `node-scripts build` does (`bundle/index.mjs`)

1. **Reads config.** From the module: `node-scripts.config.js` (`main`, `submodules`, `exports`, `symbols`, `alias`, `typescript`), `package.json` (`name`, `version`, `main`), `bnd.bnd` `Web-ContextPath` (the build fails if it is missing: `util/configuration/getProjectWebContextPath.mjs`), and `src/main/resources/META-INF/resources/language.json`. From the global `modules/node-scripts.config.js`: `imports` and `symbols`. Entry points must sit under `./src/main/resources/META-INF/resources` or the build throws (`util/configuration/getProjectEntryPoints.mjs:72-84`).
2. **Cleans** `build/node/packageRunBuild/resources/__liferay__` and `.sass-cache` (LPD-74323).
3. **CSS/Sass** (`util/sass/processSassFiles.mjs`, `util/css/processCSSFiles.mjs`). Dart Sass (a downloaded binary, with the `sass` npm package as fallback) compiles each non-partial `.scss` with load paths `bourbon`, `liferay-frontend-common-css` and `@clayui/css`. Output is `compressed` when `NODE_ENV=production` and `expanded` otherwise (`util/sass/util/runSass.mjs:16`). Source maps are always on. **`rtlcss` writes a `_rtl.css` twin** for every output. Imported `.css` URLs get a `?t=<timestamp>` (the code itself calls this "completely flawed"). Sass is skipped when no `.scss` changed.
4. **esbuild** (`util/esbuild/bundleJavaScriptMain.mjs:36-66`). The main entry and its `submodules` are bundled as `format: 'esm'`, `target: ['es2022']`, `sourcemap: true`, `entryNames: '[dir]/[name].([hash])'`, into `__liferay__/`. `.js` files are parsed as JSX, `.scss` imports become CSS, `.png` imports become empty. Types are stripped, not checked. Exports (`exports` in `node-scripts.config.js`) are bundled separately into `__liferay__/exports/…` by `bundleJavaScriptExports.mjs`, and CSS exports by `bundleCSSExports.mjs`. `process.env.USE_REACT_16` is defined from the environment (`runEsbuild.mjs:28-34`).
5. **Linking** (`util/esbuild/plugins/getLinkerPlugin.mjs`). This decides, for each bare import, whether to bundle it or link it at runtime:
   - The import path **exactly** matches a key of the global `imports` (a package another module `exports`, or a `@liferay/<module>` name): it becomes an external URL into the provider's `/o/<provider>/__liferay__/…` through a generated import bridge, so the code is shared at runtime.
   - `@liferay/<module>/<submodule>` matching a declared submodule: external URL to that submodule.
   - A `.css` import of an exported CSS file: external URL to a CSS export loader module.
   - Anything else is bundled into the module. Imports inside the module that cross its own submodule boundaries are rewritten to the submodule URL (`util/esbuild/util/CrossSubmoduleImportsChecker.mjs`).
6. **`Liferay.Language.get` plugin** (`util/esbuild/plugins/getLiferayLanguageGetPlugin.mjs`). It scans module sources for `Liferay.Language.get('literal')`, collects the keys into `build/.../language.json`, and injects `import '@liferay/language/<webContextPath>/all.js'`. **A non-literal argument is skipped with a console warning and the label is missing at runtime.**
7. **AMD bridges and metadata** (`util/amd/*`). It writes an AMD `index.js` (`Liferay.Loader.define("<name>@<version>/index", …)` re-exporting the ESM bundle), export bridges, a `manifest.json` (flags `esModule`, `useESM`) and a `package.json`, so legacy AMD consumers (`Liferay.Loader.require`, `<aui:script require>`) still resolve ESM code.
8. With `CREATE_BUNDLE_REPORTS` set, Sonda writes bundle-size reports to `build/bundle-reports/`. Every esbuild config used is dumped to `build/node-scripts/esbuild/config/<name>.json` (`runEsbuild.mjs:56-70`).

### The global config: `modules/node-scripts.config.js`

- It is generated (header "AUTO-GENERATED: DO NOT EDIT"), with a `hash`. `util/createGlobalConfig.mjs` builds it from every module's `exports`, `submodules` and `symbols`. `node-scripts format` run at `modules/` regenerates it (`util/format/formatters/formatGlobalNodeScriptsConfig.mjs`), and `checkFormat` fails when it is stale.
- `symbols` overrides the export names the build infers for a package. It is needed when the package cannot be `require`d in Node (it touches `window`), when it is polymorphic, or when it needs an explicit `default`. A module may only declare `symbols` for packages it `exports` (`createGlobalConfig.mjs:31-37`).
- Most shared third-party packages are exported by `frontend-js-dependencies-web` (`@liferay/js-api`, `dompurify`, `moment`, `date-fns`, `qs`, …), React by `frontend-js-react-web` (`react`, `react-dom`, `react-16`, `react-18`, `formik`, `prop-types`, …), Clay by `frontend-js-clay-web`.

### CSS from JS

- `import './Foo.scss'` makes the linker emit an inline ESM stub. It builds the URL of the compiled CSS, switches to `_rtl.css` when `document.documentElement` has `direction: rtl`, resolves it against `import.meta.url`, and appends a `<link>` carrying `Liferay.CSP.nonce` (`util/esbuild/util/getCSSLoadJavaScript.mjs`).
- Server-side CSS is still referenced through portlet properties such as `com.liferay.portlet.header-portlet-css`. That part of the old guideline is unchanged and belongs to the resource-serving topic.

### Minification is build-time only

- JS: esbuild minifies when `NODE_ENV=production` (`runEsbuild.mjs:37`, and `bundle/custom.mjs:44` for `build:custom`). Themes use terser. CSS: Sass `compressed` style.
- The server does **not** minify JS any more (see `dev-environment-and-debugging.md`). A JS file that skips the node-scripts bundle (a legacy file under `META-INF/resources`, a `Liferay-JS-Resources-Top-Head` script) ships unminified.

### Dependency policy (enforced in code)

Source Formatter (`modules/util/source-formatter/src/main/java/com/liferay/source/formatter/check/JSONPackageJSONCheck.java`) checks `package.json` files under `modules/apps`, `modules/dxp/apps` and `modules/private/apps` that sit next to a `build.gradle`/`bnd.bnd` and have `scripts`:

- `devDependencies` gives `Entry "devDependencies" is not allowed` (`:69`). Current suppressions are in `source-formatter-suppressions.xml:192,196`, `modules/apps/frontend-js/source-formatter-suppressions.xml:7-8`, `modules/apps/commerce/source-formatter-suppressions.xml:24-28`, `modules/dxp/apps/portal-workflow/source-formatter-suppressions.xml:5`. About 9 non-Clay module `package.json` files carry `devDependencies` today. They are either suppressed (`frontend-js-react-web`, `frontend-js-clay-web`, `analytics-client-js`, `commerce-frontend-js`) or skipped because they have no `scripts` (the three generated `*-client-js` REST clients).
- `build` must end with `build`, `build:custom` or `webpack` (themes: `build:theme`). `checkFormat` must end with `--check`/`check`/`check:ci`. `format` is required.

node-scripts `format` at `modules/` (`util/format/formatPortal.mjs`, part of `checkFormat` / `portalYarnCheckFormat`, run by `portal-impl/build.xml:881`):

- `modules/package.json` must not have `dependencies` (`FORBIDDEN_ROOT_PACKAGE_JSON_SECTIONS.mjs`). Its `devDependencies` may only be `@types/*`, keys of `ALLOWED_PACKAGE_VERSION_DIVERGENCES`, or entries in `ALLOWED_ROOT_PACKAGE_JSON_DEPENDENCIES` (`eslint-plugin-react-compiler`, `jsdoc`, each with a written reason).
- `@types/*` may only be declared in `modules/package.json` (`formatPackageJSONTypesLocation.mjs`).
- Versions must be exact, except Clay (`formatPackageJSONExplicitVersions.mjs`, `ALLOWED_RANGE_VERSIONED_PACKAGES.mjs`).
- A dependency must have the same version in every module, unless it is listed in `ALLOWED_PACKAGE_VERSION_DIVERGENCES` (`formatPackageJSONVersionAlignment.mjs`).
- `alloy-ui` is only allowed in the three listed migrating projects ("Do not add new entries", `ALLOWED_AUI_DEPENDENT_PROJECTS.mjs`).
- No nested workspaces. The workspace project set must match the `EXPECTED_YARN_WORKSPACE_PROJECTS.mjs` snapshot.
- `resolutions` must be selective and listed with a reason (currently none, `ALLOWED_ROOT_PACKAGE_JSON_RESOLUTIONS.mjs`).
- `yarn.lock` must not reference a local registry (`formatYarnLock.mjs`).
- Per-module tool config files are forbidden (`.babelrc*`, `babel.config.*`, `.eslintrc` variants other than `.eslintrc.js`, `.prettierrc*`, `.stylelintrc*`, local ignore files; `formatConfigFileNames.mjs`). An `api` submodule must live at `js/api/api.{js,ts}` (`formatAPISubmodules.mjs`).
- TypeScript is type-checked here (`formatTypeScript.mjs`, skippable with `--ignore-typescript`), not during `build`.

## Review checklist

- **New runtime dependency in a module `package.json`**: is it already exported by a provider (`frontend-js-dependencies-web`, `frontend-js-react-web`, `frontend-js-clay-web`, …)? If so, import the exact exported specifier so it is shared. If it is not, it gets **bundled into this module**, and a second module adding it later duplicates the code and the state. Ask whether it should be exported from `frontend-js-dependencies-web` instead. Also check: exact version, the same version as other modules, a `modules/yarn.lock` change in the PR, license and size (`CREATE_BUNDLE_REPORTS=yes` and `node-scripts report:dependencies` can measure it).
- **Imports of a deep path of a shared package** (`react-dom/server`, `@liferay/frontend-js-web/lib/x`, `date-fns/locale/…`): the linker matches the full specifier exactly, so a deep path that is not in `exports` is bundled locally, and for a `@liferay/*` module that means a private copy of the other module's source. `@liferay/portal/no-cross-module-deep-import` (`modules/.eslintrc.js:81`) catches the `@liferay` case. For third-party deep imports, ask for an `exports` entry in the provider or a different import.
- **Singletons** (React, Clay provider, `@liferay/frontend-js-state-web`, `@liferay/js-api`): a bundled copy breaks hooks and context, or splits state. Make sure they resolve to the provider and are not bundled.
- **Changes to `exports`, `submodules` or `symbols` in a provider's `node-scripts.config.js`**: the PR must also contain the regenerated `modules/node-scripts.config.js` with a new `hash`. A hand edit of the global file (content changed, `hash` unchanged) is a defect. Removing or renaming an export breaks every consumer at runtime (the import cannot be resolved). That can include external Client Extensions that import exported packages such as `@liferay/js-api` through import maps. Treat it as a public API change and ask for a deprecation path. A new `symbols` entry is exhaustive: if consumers use `import X from`, it must list `default`.
- **Edits to `modules/frontend-sdk/node-scripts/**`**: these affect hundreds of modules and all generated output (bridges, hashes, URL shapes). Ask for a full build (`ant all`) or `/pr-check`'s full-portal-build, and keep the output deterministic. `format` keeps the package's `com.liferay.sha256` field up to date. For linker changes, ask for before/after bundle reports.
- **`build` script other than `node-scripts build`**: `build:custom` (raw esbuild config in `node-scripts.config.js` `customBuild`) is for standalone, non-linked output (`frontend-js-svg4everybody-web`, `analytics-client-js`, `portal-url-builder-impl`). It skips linking, AMD bridges and the `Liferay.Language.get` plugin. Ask why the standard build does not fit. Custom configs set their own `target` (often `es2020`) and `sourcemap`.
- **New `devDependencies` / Source Formatter suppression for `JSONPackageJSONCheck`**: needs justification (generated REST clients and React test backends are the existing precedents). A suppression also turns off the `build`/`checkFormat`/`format` script checks for that file.
- **New root `modules/package.json` devDependency or `resolutions`**: only `@types/*`, a divergence entry, or an allowlisted tool with a written reason. A resolution must be selective and is "a last resort".
- **Per-module tool config** (`.babelrc`, `webpack.config.js`, `.prettierrc`, a local `.eslintignore`): format rejects most of them, and the others do nothing because the build is esbuild with fixed options. Ask the author to remove them.
- **`Liferay.Language.get(variable)`** or template literals with `${}` in module JS: the key cannot be collected and is missing at runtime. Ask for literal keys (map variable keys to literal `Liferay.Language.get('…')` calls).
- **`process.env.NODE_ENV` checks**: compare only against `'development'`/`'production'` string literals. A typo silently makes dead code. Real example: `ai-creator-openai-web/.../AICreatorModal.tsx:102` compares against `'developm̀ent'` (with a combining accent), which can never match.
- **Entry points** (`main`, `submodules`) must be under `src/main/resources/META-INF/resources`. `bnd.bnd` must keep `Web-ContextPath`, because the build and all URLs depend on it. Renaming `Web-ContextPath` or the npm `name` changes the runtime URLs and AMD module names that consumers use.
- **SCSS changes**: an `_rtl.css` twin is generated automatically. Do not hand-write RTL files. Check that directional properties survive `rtlcss` (use `/*rtl:ignore*/` only when intended).

## Use cases and how-tos

- **Standard module**: `package.json` scripts `"build": "node-scripts build"`, `"checkFormat": "node-scripts format --check"`, `"format": "node-scripts format"`, `"test": "node-scripts test"`. `node-scripts.config.js` contains at least `main: './src/main/resources/META-INF/resources/js/index.ts'`.
- **Expose a package or symbol to other modules**: add it to `exports` in the provider's `node-scripts.config.js` (add `symbols` if the inference fails), run `yarn format` (`node-scripts format`) from `modules/`, and commit both files.
- **Expose a sub-entry of a `@liferay` module**: `submodules: {foo: './src/main/resources/META-INF/resources/foo.ts'}`. Consumers import `@liferay/<module>/foo`.
- **Development build of one module**: `gradlew deploy -Pnodejs.node.env=development` from the module, or set `nodejs.node.env=development` in `build.<user>.properties` and run `ant setup-sdk`. From a shell, `yarn build` with no `NODE_ENV` already gives a development build (it does not deploy).
- **Find why a package is bundled or duplicated**: `CREATE_BUNDLE_REPORTS=yes ant all` (or a module build with the env var), then `node-scripts report:bundle-imports`, `report:bundle-sizes [--with-internals]`, `report:dependencies` from `modules/`. Read `build/node-scripts/esbuild/config/main.json` for the exact esbuild config.
- **Build timing**: set `LIFERAY_NPM_SCRIPTS_TIMING=<dir>`, then run `node-scripts report:build <dir>`.

## Pitfalls and side effects

- Gradle `packageRunBuild` up-to-date inputs: the module `package.json`, the source dir, the workspace `yarn.lock`, `modules/frontend-sdk/node-scripts/package.json` (`PackageRunBuildTask.java:36-130`), the module and global `node-scripts.config.js` and (for SCSS modules) the Clay SCSS tree (`modules/build.gradle:272-288`). node-scripts **code** is not an input. A change to it only invalidates builds through the `com.liferay.sha256` digest in its `package.json` (`util/digestNodeScripts.mjs`, `formatNodeScriptsHash.mjs`). A node-scripts PR that does not refresh that field leaves every module `UP-TO-DATE` with stale output.
- Sass compilation is skipped when no `.scss` changed (an mtime/hash check against the build dir). Changing only a load-path dependency such as Clay CSS relies on the Gradle input wiring in `modules/build.gradle:281-287`.
- Every non-entry file under `META-INF/resources` is copied into the JAR as-is, so source `.ts`/`.tsx` and any stray file ship and are publicly served under the web context.
- The `?t=<timestamp>` appended to CSS `@import url(...)` changes on every Sass build. This hurts HTTP caching and produces diffs in build output.
- AMD bridges keep old `Liferay.Loader` consumers working. The AMD loader is deprecated behind feature flag `LPD-48372` (on by default, type `deprecation`, `portal.properties:6892,7566-7571`). Code that still depends on the AMD module name (`<name>@<version>/index`) breaks when the loader is removed.
- Changing `version` in a module `package.json` changes its AMD module ID and generated metadata. It does not affect ESM URLs, which use the hash.

## Not carried over

- Soy build phase, `metalsoy`, Babel config defaults, webpack phase, `liferay-npm-bundler` presets (`liferay-npm-bundler-preset-liferay-dev`), `liferay-npm-bridge-generator` / `.npmbridgerc`, `npmscripts.config.js` validation: obsolete. None of them exist in portal module builds (`git ls-files` returns 0 for these config files; `bundle/index.mjs` has no such phases).
- "Bundler v2 imports" cross-link: obsolete with the bundler.
- Theme Generator (Yeoman) and the `liferay-theme-tasks` gulp pipeline in detail (themelets, `gulp deploy`): not used in portal. It belongs to a separate external-themes topic (`projects/js-themes-toolkit`) if needed.
- Lerna case study (package counts, BundlePhobia numbers): an illustration from 2020 with stale numbers. Its point is kept in the dependency checklist.
- Links to `liferay-npm-tools` / `liferay-js-toolkit` GitHub trees: dead or archived references.
- `JSLoaderConfigServlet` / `JSBundleConfigServlet` minifying their output: moved to the dev-environment topic. The first no longer exists, and the second does not minify.
